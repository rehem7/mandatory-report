# 对话转报告的准确性改进方案

## 原有问题

手动“从对话整理报告”将用户消息交给模型提取字段；对话中的自动草稿则由模型调用 `prepare_report_draft` 工具生成。两者均为模型辅助预填。接收端 `assess()` 的关键词规则是另一条提交后的演示研判流程。

目前已有未知留空、字段白名单和格式检查，但缺少字段对应原话的强制校验。泛化咨询、条件假设、转述和推测仍可能被写成具体事件；自动草稿还可能混入模型自己的建议。

## 已实现流程

1. **统一入口**：手动按钮与自动工具均调用同一抽取服务；只允许引用当前会话的用户消息。AI 回复、检索材料与记忆不能直接作为本次事件证据。
2. **保留出处**：每个候选字段返回值、用户消息编号、原文片段及表述性质，例如亲历观察、当事人原话、转述、推测或假设。
3. **服务端校验**：确认引用片段确实存在，校验日期与地区的规范化关系。无来源的字段留空并说明原因；有冲突的字段提示用户只保留确认后的一个值。存在引文也不等于真实发生，仍须用户确认。
4. **区分内容**：已知情况、待核实信息和处置建议分开呈现。事件经过保留“据其陈述”“尚未确认”等限定，建议不写入事实描述，事件类型允许暂不选择。
5. **先确认再写入**：生成后展示候选字段及原话，用户逐项修改、确认，点击“使用这些信息填写表单”后生成草稿；最终提交继续由表单独立确认。

手动与自动入口现共用独立抽取服务，只传入本会话编号后的用户消息。每项候选包含原话、消息编号与表述性质；服务端检查引用存在性、字段规范化及部分否定/假设/建议语境。事件经过使用原话所在完整句，避免摘录时丢失否定或转述限定。类型允许留空，多个冲突值由用户选择。

用户在核对窗口逐项选择和修改，明确确认后才生成表单草稿。转述和推测单独展示，写入事件经过时保留“待核实”标记；建议和假设不可选择。对话变更后旧核对结果失效，确认记录保留所选原话与用户修改标记。最终提交仍是独立动作。

抽取格式错误会明确提示重试或手动填写，不回退为关键词补全。未通过校验的字段会显示留空原因。旧版本自动草稿需重新提取与核对。

## 验收样例

| 输入情形 | 预期行为 |
| --- | --- |
| “如果发现孩子被虐待，教师怎么办？” | 识别为咨询，不生成已发生的事件 |
| “未发现家庭暴力，只是同学争吵” | 保留否定含义，不推断家庭暴力 |
| “我猜可能受伤，听邻居说的” | 标为推测或转述，不改写成亲历事实 |
| AI 曾建议报警、就医、保存证据 | 不把建议写为已经完成的行动 |
| 用户没有提供时间、年龄或地址 | 留空并列为待补充，不自动补当天日期 |
| 用户后续纠正地点或事件经过 | 显示更正与冲突，使用用户确认后的版本 |
| 同一段对话分别触发手动与自动整理 | 使用同一事实抽取与校验规则 |

上述场景已纳入固定虚构数据的自动化回归，另覆盖跨账号访问、重复确认和伪造候选项。规则检查与模型分类不能证明现实事实真伪，也不能完整理解所有复杂语境；保守留空和用户核对仍是必要步骤。尚未进行真实业务数据的大样本准确率评估，不声称已达到某一准确率。

实现入口：`report-extraction.js`、`portal-api.js`、`public/report-review.js`。案例库接入建议见 [CASE_LIBRARY_PLAN.md](CASE_LIBRARY_PLAN.md)。
